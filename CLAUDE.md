# CLAUDE.md — WebSACO Finanzas · Backend

> **Read `../CLAUDE.md` first.** Those rules apply here and aren't repeated below.

Instructions for AI coding agents in this repo. Human setup docs live in `README.md`.

## What this is

REST API for WebSACO Finanzas (billing, receivables, reports). Stack: Node 22, NestJS 11, TypeScript, MongoDB/Mongoose, Redis (ioredis), Firebase Admin (token verification, plus user creation for staff/resident sign-in provisioning and custom tokens for access links), `pdf-lib`, `pdfjs-dist` (reading the block-billing PDFs), SendGrid, `@nestjs/schedule`. Target: Cloud Run.

Scope so far: config, Mongo/Redis, health, Firebase auth against local accounts, the catalog/identity model (coproperties, units, parties, charge concepts, accounts/assignments), tenant context + CASL + the API contract convention, and the financial documents (facturación, recibos, notas contables/crédito/débito, PDFs, accounting ledger, estado de cuenta, cartera aging, auditoría). Since the fusion, also the Administración modules (PQR, reservations, documents, announcements, tasks, maintenance, activities, roles, staff team and resident provisioning, the resident portal) behind the `administracion` licence, and the native invoice send (`envio-facturas`). No queues: delivery runs inside the request, resumable.

The plain `node scripts/*.js` files in `scripts/` are NOT covered: they are run by hand with `node --env-file=<file>` and read their own `MONGODB_URI`.

Before declaring a change done: `npm run typecheck && npm run lint && npm test` → delegate per your user-global `~/.claude/CLAUDE.md` routing rule (Test/Lint/Build Execution Routing, not this repo's `../CLAUDE.md`), do not run directly via Bash.

No Docker, no local database — Mongo (Atlas) and Redis (Redis Cloud) are managed services reached over the network. `npm run start:dev` is the whole story. Don't add `docker-compose.yml` or a `start:local-services` script back; both were removed on purpose.

## Non-negotiable rules

1. **No silent config fallbacks.** Every required env var is in `src/config/env.validation.ts` (Joi) and fails loudly at boot when missing — never `process.env.X ?? 'default'` in `app.config.ts`. New required var → new Joi rule + `.env.example` entry.
2. **Never require a secret nothing reads**, and never add one silently either — `FIREBASE_SERVICE_ACCOUNT_BASE64` boots-fails without a Joi rule, no "unauthenticated fallback".
3. **Every request input goes through a DTO.** Global `ValidationPipe`: `whitelist`, `forbidNonWhitelisted`, `transform`. An untyped body/query is a bug.
4. **Liveness never checks dependencies.** `GET /health/live` stays dependency-free so a slow Mongo/Redis triggers a readiness failure, not a restart loop. Dependency checks belong in `/health/ready`.
5. **API prefix is `api/v1`**, set once in `main.ts` — controllers never repeat it.
6. **CORS is always on** (`src/config/cors.ts`): explicit allow-list from `CORS_ORIGINS` in prod; any localhost in dev, since Vite's port moves. Adding a new client header (coproperty id, idempotency key) means updating `allowedHeaders` in the same change.
7. **Responses use the `{ statusCode, data }` envelope** the frontend unwraps in `client.ts`. Never return a bare payload.
8. **The tenant never comes from the client.** See "The tenancy law".
9. **Nothing financial is ever deleted.** See "The audit law".
10. **A manual step per environment is declared in one place and detected by readiness.** Any change that needs something done by hand in each environment — a seed, a migration, a new env var, a new secret — must (a) be listed under a "Pasos por ambiente" section in the commit/PR description AND in the relevant runbook (`docs/runbooks/`), and (b) wherever it can be checked, be detected by `GET /health/ready` (an indicator in `modules/health/` that fails naming the exact setting or command to fix, never echoes a value, answers fast instead of waiting on a dependency, makes no network call to a third service, and reports itself as skipped when the feature it guards is disabled in that environment), so a missed step is loud at deploy time instead of a silent failure later. Model: `integracion-comptable.health.ts`. If a step cannot be checked, say so in that same section. Cannot be checked, and says so: the permission-key conversion of the team-delegation release (`docs/runbooks/equipo-delegacion.md`), because after the deploy a Finanzas key on a `personal` row is a legitimate grant and no indicator can tell it from a missed strip. The step is only PARTIALLY guarded, against a late re-run, not a missed run: the script's pre-deploy modes (default listing and `--aplicar`) refuse with exit code 2 and write nothing when the data holds the marker that `--aplicar --retirar-gestionar` leaves (collection `marcas_despliegue`) or an audit entry with `entidadTipo: 'rol'` or a `detalle` (only the new backend writes them). Not detected: a deployed backend where no role or key change has been written yet and `--retirar-gestionar` has not run, or a database whose audit entries were purged; there the pre-deploy modes still run, so the deploy order stays the real protection. Born from a sibling service's production 500 on `POST .../lotes` (a seed nobody ran, no log, nothing in readiness) — Finanzas' own blind spot was that its call to Comptable logged only `HTTP 500 (inesperado)`, so `ComptableClient` now also logs Comptable's own `message` (5xx only, truncated, never the raw body).

## This system stands alone

Two of three sale configurations involve zero integration with the building-management system, so Finanzas must be complete alone: it owns all its data and never reads a catalog out of the other system. Where both exist, the integration is outbound-only and optional — Finanzas feeds the other system, never the reverse — enabled per coproperty (the flag is "this coproperty *also* uses the other system", not the other way round). The domain code must not know the other system exists; publishing lives at the edge, reacting to what the domain already recorded. Deleting the publishing side entirely should leave every financial module compiling, tested, and correct — that's the test for whether it's separated properly. Absence of the integration needs no fallback or warning state; for most clients it's simply not part of the product.

Since the fusion with the building-management product, Administración lives inside this backend as contracted modules, so the old HMAC edges toward that system (invoice publication, holders pull) are gone: invoices reach owners and tenants through `modules/envio-facturas/` (explicit mark + process, delivered inside the request, audited), and residents read them under `/portal/facturas` only after staff released them. The integrations panel (`modules/integraciones-panel/`) still links a coproperty to Comptable only.

## The tenancy law

Every query on tenant-owned data resolves the tenant from the request context, never the payload:

```ts
const copropiedadId = this.tenant.resolveCoPropertyId();
return this.model.find({ copropiedadId }).exec();
```

- `TenantContextService.resolveCoPropertyId()` returns an **`ObjectId`**, not a string — a filter built from the string form matches nothing and silently returns an empty list, the worst failure mode (a 60-unit building reads as empty, and nobody suspects the query). Never hand-build from `activeCoPropertyIdOrNull()` (the string form, for callers that must branch on absence).
- A client-supplied `?coPropertyId=` may only ever *confirm* the active tenant, never set it.
- No fallback to "the first coproperty" when nothing is active — that's a cross-tenant leak wearing a helpful face. No active tenant → throw.
- **`findById(x)` is the recurring real bug here** — it filters only by `_id`, correct only when `_id` IS the tenant id (`copropiedades.findById(copropiedadId)`). For any other tenant-owned lookup (`Inmueble`, `Tercero`, etc.), use `findOne({ _id: x, copropiedadId })`. This exact mistake has shipped and regressed multiple times in this codebase's own history (`consultas` module) — check for it specifically on any new "fetch by id I already have" lookup.

`FirebaseAuthGuard` writes the tenant into CLS after checking the requested `X-CoProperty-Id` against the caller's live assignments via `AccesoService` — a header naming a coproperty they can't use is **rejected**, never silently ignored. Access resolves as a union (a per-building grant and a per-entity grant both reach the same place, merging where they overlap); an inactive assignment, company, or building removes access at any hop.

**Choosing a coproperty:** the list is this system's own `(accountId, copropiedadId)` pairs — local, no join needed. The listing endpoint must not itself require an active tenant (that's a deadlock: you need the list to pick one). The guard revalidates the header against live assignments on every request — a remembered choice in the client is a request, never a grant. One assignment → auto-select. Zero → say so plainly, never render an empty picker.

## The audit law

**No financial document is ever physically deleted.** Voiding is a state transition (`estado: 'anulada'`) plus an append-only log entry (who/when/why). This is enforced in the vocabulary: the financial verbs (`VERB_TO_ACTION`) have no `eliminar`, and `remove` is vetoed on every financial subject after the grants (platform admins included), so no route over a financial document can be granted it. `eliminar` → `remove` exists ONLY for Administración segments (`VERB_TO_ACTION_ADMINISTRACION`: PQR, tasks, documents of the building library…, which are not financial records). `annul` is the sanctioned replacement, kept separate from `update` so a role can hold one without the other. Don't add `eliminar` to the financial verbs or lift the veto — `permission-map.spec.ts` fails on purpose if someone does. `purge` (verb `depurar`) is the guarded hard delete of pre-document data (an unused charge concept, a unit with no Factura, a lote cancelled before it issued anything), never `remove`: holding it does not lift the veto, and the services behind those routes still refuse anything already issued.

**Narrow exception — undoing a failed `consolidar` run** (`LotesFacturacionService.deshacerConsolidacion`, confirmed with accounting). If a consolidación fails (a tanda's transaction, or an exception escaping the run), the lote is put back to zero: every Factura of that `loteId` plus its SaldoCartera increments, `CarteraPorDocumento`/`SaldoTotalDocumento` rows and asientos are physically deleted, and the invoice counter is rewound to where `reservarBloqueFacturas` found it (one conditional `updateOne`: only if it still equals what the run left, so it can never go up or clobber numbers someone else reserved). `cancelar` runs the same undo for a lote that already has Facturas. The exception stops exactly there:

- Only records created by the consolidación run that just failed, or by an interrupted/legacy run of the SAME lote — never anything issued, PDF'd or published.
- Guarded, not assumed: if ANY Factura of the lote is referenced by an `AplicacionCartera` (any state), a `NotaCredito`, a `NotaContable` or a generated PDF (`PresentacionDocumento.generatedAt`), or if the LOTE itself has a generated FV PDF (`PresentacionDocumento` anchored on the lote id), a `PublicacionLote` row (WebSaco3 outbox) or any Factura with a `printSnapshot`, the whole undo is refused before deleting anything. A Factura with no asiento (legacy orphan: unknowable whether its saldo was applied) also refuses it, asking for manual reconciliation. The guard fails closed (missing models → refuses). `cancelar` is refused while the lote has a running consolidación (`progreso` non-null). A lote may mix numbering sources, so the counter is rewound per `resolucionId` group (null = FV fallback), only over the contiguous run ending at that group's highest number. Known limitation: if a later block of the undo fails, the counter is NOT rewound and `facturaIds` is re-read from the remaining Facturas; a later `cancelar` derives from those only.
- Every reversal writes an `AuditoriaService` entry (`accion: 'revertir'`, `entidadTipo: 'lote-facturacion'`, lote and number of Facturas).
- `ReiniciarCicloService` is a different, separate exception: it wipes every financial document of the ACTIVE coproperty, with no coproperty whitelist (the 0001-0003 sandbox restriction was removed on purpose, 2026-10-09, so it can run on a real client's building). Its only gate is `PlatformAdminGuard` on `ReiniciarCicloController` — not CASL, so no role a customer administrator could hold reaches it — plus the frontend's type-to-confirm step; it also refuses to run during a consolidación or a recibos application and writes an audit entry (`accion: 'reiniciar'`). Neither exception is a template for deleting anything else.

## Authentication

`@UseGuards(FirebaseAuthGuard, PoliciesGuard)`, in that order (`PoliciesGuard` reads `request.user`). Health endpoints carry no guard.

The guard verifies `Authorization: Bearer <token>` with `verifyIdToken(token, true)` — `checkRevoked: true` costs one round trip but gives immediate lockout on a disabled account instead of waiting up to an hour for expiry. Don't drop it. Every verification failure returns the same opaque 401 — a probe shouldn't distinguish expired/revoked/forged; detail goes to the log.

**Firebase writes happen in exactly one place: `FirebaseUsuariosService`**, used by `/equipo` (staff of a coproperty) and `/residentes` (owners and tenants) to create the sign-in with a random password nobody sees; people enter through an emailed access link or "forgot password". An existing identity is never taken over silently (residents need `vincularExistente: true`; bulk provisioning never links). Nothing else may call `createUser`/`updateUser`/`deleteUser`/`setCustomUserClaims`, and no seed writes to Firebase — the identity pool is shared with another system's real users (see `../CLAUDE.md`). `EnlaceAccesoService` mints custom tokens for access links (it reads and writes no user); the public redeem is `POST /auth/enlace/canjear` (rate-limited, opaque 401), and it never issues a link to a platform admin, an inactive account, or an account with Finanzas reach in ANY coproperty or a non-`personal` assignment anywhere. The audience is therefore residents and team members holding Administración keys only: because a `personal` member can now hold Finanzas keys, the first one granted in any building ends the link, built or already emailed (it is checked again at redeem); that person gets the invitation without a button and signs in with their own e-mail («Olvidé mi contraseña»).

**Two identities, not one:** the provider answers "who are you", the local `Account` answers "what may you do here". A valid token with no local account is authenticated and entitled to nothing — the guard lets it through with an empty permission list rather than rejecting, because real users of the other system can obtain valid tokens for this API and must land on nothing (not an error).

`CuentaService.resolverPorToken()` matches by provider uid, falling back to email only for first-claim of an admin-prepared account (safe: the provider allows one account per address). `email_verified` is deliberately not checked — console-created accounts start unverified with no way to change it. `ROOT_ADMIN_EMAIL` is only the input to `npm run seed:admin` (creates the first platform-admin account so someone can create others); it never touches the identity provider.

## Authorization

`@CheckAbility({ action, subject })` on the route, `PoliciesGuard` in the controller's own `@UseGuards` (never a global `APP_GUARD` — must run after auth). **Enforcement is default-deny**: under `PoliciesGuard` a route with no `@CheckAbility`/`@CheckAnyAbility` and no `@AuthenticatedOnly()` answers 403, and `casl/route-policies.spec.ts` fails for any route that does not declare exactly one policy (public, signed service, platform admin, authenticated-only, portal, or CASL + `@Modulo`). The `@Public()` routes are pinned by name in that spec, each with its reason. `casl/route-collisions.spec.ts` fails when two controllers can resolve the same request (same verb + path, or a `:param` that swallows another controller's static segment): `/documentos` belongs to Finanzas (document types) and the Administración library lives at `/documentos-administracion` (its permission prefix), after the two once shared `@Controller('documentos')`. Residents carry no permissions and use `/portal/*` behind `PortalGuard` (current holder of an active unit of the active coproperty). A route belongs to ONE module (`@Modulo`) unless it is shared on purpose: `@ModuloAlguno('finanzas', 'administracion')` accepts either. It is pinned by name in `route-policies.spec.ts` (a new shared route fails there until added on purpose): `GET /portal/unidades` (every resident form starts from it, no financial data), the whole of `/equipo` and `/roles` (a team is managed whichever product the building bought; the `usuarios.*` / `roles.*` abilities are still required, and `/residentes` stays Administración only) and `GET /catalogo-permisos/finanzas`. Invoices and the statement stay `@Modulo('finanzas')`. Those `usuarios.*` / `roles.*` keys are Administración keys, so in a Finanzas-only coproperty the main account has none until a platform admin ticks them in the platform Usuarios screen (an access's permissions, «Equipo y roles»); no automatic grant exists. `perfil` (`administrativo` / `personal`) only says WHO MANAGES the row (only a platform admin edits an `administrativo` one, `/equipo` manages `personal` ones) and drives the header label, notice recipients and the access-link rule below; it never limits which keys the row may hold. A `personal` row may carry Finanzas keys, on write (`/usuarios` judges the catalog only, no cap: `POST /usuarios` and the two assignment endpoints require every NEW key to be offered, and `PATCH /usuarios/:id` is account-only and judges no keys; `/equipo` and `/roles` judge by the cap in the next paragraphs) and on read (`AccesoService` lists every KNOWN key, direct plus those of the roles the row names for its own coproperty; unknown keys are dropped). A key of a module the coproperty did not contract is stored and listed but inert, since every route carries its `@Modulo`. A role may carry any offered key, under the same cap as `/equipo`.

**The delegation law of `/equipo`** (`EquipoService`, pure rule in `casl/delegacion.ts`): a member's *effective* keys are their direct keys plus the keys of their roles (roles of the ACTIVE coproperty only), restricted to *offered* keys (the Finanzas catalog plus the Administración catalog). Every create, update, role attach/detach and deactivation is judged on the **symmetric difference** of the effective set before and after, and each changed key must be held by the caller **by exact key** (`tareas.gestionar` never stands in for `tareas.ver`; Finanzas has no covering key at all). Keys that do not change are never judged, so re-sending a key you do not hold, unchanged, is fine; the platform admin is exempt from the cap but not from the catalog. A key that is NEW must be offered (400 otherwise, decided before any 403, so nothing is created, not even the Firebase identity); a stored legacy or not-offered key (`facturas.gestionar`, `inmuebles.aprobar`) travels back untouched and is never judged. Deactivating a member requires holding every key they have (`after = []`); a member with an empty effective set can always be deactivated, and an already inactive one answers 200 with no write and no audit. `actualizar` and `desactivar` write only while `permisos` and `roleIds` are still what the check read (and the row is still active), else 409 «El acceso cambió mientras se procesaba»; a rename alone touches no keys and carries no condition. Reactivating an inactive `personal` row judges the new grant against an empty "before". Nobody changes their own access: `actualizar`, `desactivar` and `crear` (adding or re-linking an existing account) all answer 403 «No puedes modificar tu propio acceso» when the account is the caller's. Every key-changing call writes an audit entry with `detalle { agregadas, quitadas }` (the sets the cap judged, sorted). `crear` (the assignment, new or reactivated), `actualizar` (keys, rename of the Account, entry) and `desactivar` each write the change and the entry in ONE Mongo transaction, so a failed audit write leaves nothing saved and a retry cannot skip the entry. Only the Firebase identity and the Account of a person who is new cannot join it and are written first: if the transaction then fails they stay, inert, and the retry meets the existing-account rule (`CUENTA_EXISTENTE`, `vincularExistente`) instead of creating a second identity. The `permisos` array of an Equipo or Roles body is capped by `MAX_CLAVES_ASIGNABLES` (`permisos-catalogo.ts`: Finanzas catalog + Administración catalog + `MARGEN_CLAVES_HEREDADAS`, 116 today), derived and never a literal, so a request that ticks every box always fits and stored keys that travel back untouched have room; each key is at most 80 characters. The conditional writes share `filtroListaExacta` (`casl/filtro-lista-exacta.ts`).

**Roles follow the same cap** (`RolesService`): a role is a bundle of any offered keys (Finanzas and Administración; `GET /roles/permisos` still lists only the 30 Administración ones), and `create` / `update` are judged on the ROLE's own keys, by exact key, add and remove alike, with the same 400-before-403 order, the same "unchanged keys are never judged" and "platform admin exempt from the cap, not from the catalog". It is not fanned out to the holders: the per-key rule gives the same answer for each. Whoever holds a role may change its name but not its `permisos` (403, even with an identical list); the `permisos` write is conditional on the keys the check read (409 for everyone, platform admin included). Changing a role's `permisos` is also refused (403 «Este rol lo tiene una cuenta que se administra desde la plataforma: sus permisos no se pueden cambiar aquí») while ANY active holder of it in this coproperty is a non-`personal` assignment (legacy rows without `perfil` count as `administrativo`; one that an earlier release moved from `personal` may still carry `roleIds`, but no Usuarios call writes them any more: reactivating a row clears them) or belongs to a platform-admin account, because the role's keys reach those rows and the team screens must not touch them; a platform admin is exempt, a rename or the same keys sent again (no effective change) is allowed, and the check runs only when keys really change. Deleting a role with no active holder needs no cap, since it changes nobody's effective set. `create`, `update` and `remove` all write an audit entry (`entidadTipo: 'rol'`, `accion: 'eliminar'` for deletion, `detalle` as above; for a deletion `quitadas` is what the role carried), never when the request was refused, and in ONE Mongo transaction with the change (the `inmuebles-baja` pattern: `connection.startSession()` + `withTransaction`, `AuditoriaService.registrar(entry, session)`), so a failed audit write leaves nothing saved.

**Platform Usuarios manages a LIST of assignments that add up** (`AsignacionesUsuarioService`, `modules/usuarios/`; the owner's decision, so no "primary" row exists anywhere). `GET /usuarios` and `GET /usuarios/:id` carry `asignaciones[]`: every row of the account, active AND inactive, of every `perfil`, oldest first (ties by id), each with its own `id`, `estado`, `permisos` (stored, unfiltered) and `cantidadRoles` (0 on an `entidad` row); `asignaciones` is the only representation (there is no `asignacion` field, and nothing picks a "primary" row). `PATCH /usuarios/:id` is account-only: it accepts `nombre`, `esAdministradorPlataforma`, `estado` and `nuevaPassword`, a body carrying `alcance`, a target id, `permisos` or `perfil` is 400 by the whitelist, and it never reads or writes a row (`estado: 'inactivo'` disables the Firebase identity and the rows keep their own `estado`: the account is the kill switch over all of them). `POST /usuarios/:id/asignaciones` adds ONE row and `PATCH /usuarios/:id/asignaciones/:asignacionId` edits the keys and/or `estado` of ONE row (platform admin only, via the class-level `PlatformAdminGuard`), each answering the whole `Usuario`. Rules: a row is always created `administrativo`, active, with no roles; the target (`alcance`, `copropiedadId`, `entidadId`), the `perfil` and the roles are never editable (a body carrying them is 400 by the whitelist: "move" a person is adding the new target and deactivating the old row); the target must exist on POST (404; an inactive one is accepted) and a platform-admin account is refused (409). A POST on a target whose row is INACTIVE (any profile, an old Equipo row included) reactivates it in place (same id, `administrativo`, the keys sent, `roleIds` cleared, `estadoAlReactivar`); on an ACTIVE one it is 409 (no takeover of an Equipo row, no merge). `personal` rows (Equipo's) are read-only here: a PATCH on one answers 403 for keys, deactivation and reactivation alike (`accionesDesdeUsuarios`; both switches live in `usuarios/asignaciones-usuario.reglas.ts` as single pure functions, mirrored on the frontend). The only key rule is the catalog, without the delegation cap (the caller is a platform admin): `exigirClavesConocidas(after, before)`, so a NEW key must be offered (400 naming it) and a stored one that travels back is never judged. Each write is ONE single-document `create`/`updateOne` whose filter names the row by `_id` AND `accountId` and applies only while the row is still what the check read (same `estado`, `permisos`, `roleIds` and not turned `personal`), else 409 «El acceso cambió mientras se procesaba»; it never touches another row, the Account or Firebase, so an inactive ACCOUNT stays the kill switch it was. A request that changes nothing answers 200 with no write and no audit entry. Every successful write and its audit entry (`entidadTipo: 'usuario'`, `accion` `crear` for a new or reactivated row, `actualizar` for keys, `retirar` for a deactivation, `detalle { agregadas, quitadas }` over the row's effective set, empty while it is inactive) commit in ONE Mongo transaction. `POST /usuarios` still creates the account with its FIRST assignment, which stays mandatory for a non-platform-admin (400 before any Firebase call when it names no target or a malformed id, which must be 24 hex characters because `@IsMongoId` lets `0x…` through; 404 when the target does not exist, through the same `resolverDestino` as the assignment endpoint, also before Firebase), and writes that row and its audit entry, with `detalle`, in ONE transaction; the Firebase identity and the Account are written first, so a failed audit write leaves them inert and the retry meets the existing-email 409. `CrearUsuarioDto` has no `perfil` (a body with it is 400): Usuarios can only ever write `administrativo` rows, so no call here can create a `personal` one. No migration, index or env var: the unique indexes already allow one row per account and target forever. Release order of the contract removal: the list endpoints shipped first (additive), the frontend moved to them second, and the removal of the legacy single-row PATCH fields and `Usuario.asignacion` ships LAST, at least one working day after the frontend so open tabs reload; deployed earlier, the old form's save answers 400, and reverting the removal alone restores the legacy PATCH (revert it before reverting the frontend).

Permission keys are Spanish `modulo.accion` strings mapped to CASL rules in exactly one place, `permission-map.ts` — new subject → add to both `SUBJECTS` and `MODULE_TO_SUBJECT`. Which Finanzas `modulo.accion` pairs EXIST (the permission matrix draws a dash for the rest — «un inmueble no se aprueba») is `PERMISOS_FINANZAS` in `permisos-catalogo.ts`, derived from `ACCIONES_REALES_FINANZAS` (the actions some route requires per subject) and served at `GET /usuarios/permisos-finanzas` (platform admin) and, for the team screens of a building, at `GET /catalogo-permisos/finanzas` (`CatalogoPermisosController`: same array, `@ModuloAlguno('finanzas', 'administracion')` plus any-of read/create/update `Usuario` or read `Rol`; static, no tenant data, no service; the catalog is vocabulary, what a caller may give is still judged on the write). `permisos-finanzas.spec.ts` scans every controller and fails both ways: a route demanding a (subject, action) no key grants, or a key whose action no route demands; it also fails when any financial route requires `manage`. A new route with a new action, or a new financial subject (a compile error there), means updating that table in the same change — and deciding who receives the new key, because nobody gets it automatically. **Finanzas has no `gestionar` verb**: every Finanzas key is one exact action, so it can be held, given and taken away on its own (`gestionar` → `manage` stays in `VERB_TO_ACTION_ADMINISTRACION`, e.g. `pqr.gestionar`). A stored `facturas.gestionar` is an unknown key: it grants nothing and `AccesoService` omits it from `/auth/me`. The three guarded hard deletes (`DELETE /conceptos/:id`, `DELETE /lotes/:id`, `DELETE /inmuebles/:id`) require `purge` (verb `depurar`: `conceptos.depurar`, `facturas.depurar`, `inmuebles.depurar`) and applying a receipt batch (`POST /lotes-recibos/:id/aplicar`) requires `approve Recibo` (`recibos.aprobar`). The verb is `depurar` and not `eliminar` because `eliminar` → `remove` is reserved for Administración and vetoed on financial subjects; the UI may still label it «Eliminar». Unknown keys are skipped, and skipping means deny. `Inmueble`/`Tercero`/`ConceptoCobro` are distinct subjects from `Consulta` on purpose — reading the arrears report doesn't imply editing who owns a unit.

**The platform-admin layer:** `EntidadAdministradora` and `Copropiedad` sit *above* CASL and the tenancy law — a coproperty IS the unit of tenancy, so there's no active-coproperty to scope its own catalog by, and no customer administrator should ever hold a permission to edit it. Gated by `PlatformAdminGuard`, not `PoliciesGuard`/`@CheckAbility`. `EntidadesService`/`CopropiedadesService` never touch `TenantContextService` for the same reason. Same audit law applies: `estado: 'inactivo'` retires an entity/coproperty without touching anything it once administered.

## Cross-entity search, list totals and unit balances

Three read-only additions the frontend leans on. None writes anything; all three are tenant-scoped through `resolveCoPropertyId()` (secondary `SaldoTotalDocumento` / `SaldoDocumentoOrigen` lookups carry `copropiedadId` too).

- **`GET /busqueda`** (global search). The route is gated by `@CheckAnyAbility` over the seven read subjects (`Factura`, `Recibo`, `NotaCredito`, `OtraNota`, `NotaContable`, `NotaAnticipo`, `Inmueble`) — a caller who can read none gets a 403. That gate is only the door: `BusquedaService` then decides **per group** with `CaslAbilityFactory.createForUser(user)`. A group the caller may not read is **omitted from the response (key absent)**; a permitted group with no hits is `[]`. The client relies on that difference ("no permission" vs "no matches") — never answer `[]` for a forbidden group. Notas de débito are the `OtraNota` subject, as in their own controller.
- **`incluirTotales=true` on `GET /facturas` and `GET /recibos`** adds a `totales` block over the **whole filtered set**, not the page; without the flag no extra query runs and `totales` is absent. Anuladas/anulados are excluded (`estado` is forced to `emitida`/`activo`, so an explicit anulada `estado` from the caller yields zeros). The money comes from live balances — `SaldoTotalDocumento.saldoPendiente` (facturas) and `SaldoDocumentoOrigen.saldoDisponible`, `tipoDocumento: 'RC'` (recibos) — **never** the stale legacy `Factura.saldoPendiente` / `Recibo.montoSinAplicar`. A negative facturas balance (overpaid document) is floored at 0 **per document**, so it never offsets what other documents owe (same rule as the per-row display and `InmueblesSaldosService`); `saldoDisponible` cannot go negative, so recibos need no floor. The totals query reuses the page filter, including the `conSaldoPendiente` / `conAnticipoDisponible` pre-query.
- **`GET /inmuebles/saldos?ids=…`** (≤ 50 unit ids) returns the gross arrears per unit: `saldoPendiente` summed over `emitida` Facturas + `emitida` Notas Débito + `activo` Saldos Iniciales, each floored at 0; anticipos are **not** netted. A document with no `SaldoTotalDocumento` row counts 0 — this differs from cartera-por-inmueble, which recomputes from applications. An id of another coproperty (or nonexistent) gets no entry at all, so the route cannot probe foreign ids. Permission is an OR: read `Consulta` **or** create `Factura`. Declared **before** `:id` in `InmueblesController`, or the param route swallows `saldos`.

## The contract law

**Persistence and the API are both Spanish** (schema field migration in
progress — see `sdd`/plan history for tracking; until a schema file is
migrated, its fields are still English). A mapper is still the frontier
between the two, but its job is type conversion (`ObjectId` → `string`),
composing fields that don't exist on the document (e.g. `saldoPendiente`,
read live from `SaldoTotalDocumento`/`CarteraPorDocumento`, not a `@Prop`),
and acting as a security boundary — never language translation. Shapes go in
`src/contracts/index.ts`; each module owns a `<module>.mapper.ts` of pure
functions. A controller returns mapper output, never a Mongoose document.

This reverses the original "persistence is English" rule, which drifted into
an inconsistent English/Spanish mix in the newer financial-document schemas
and was never actually enforced there. Consolidating on Spanish (not
English) matches where the codebase already drifted and how its primary
maintainer works.

**Resolved — the structural/duck-typed contracts below are now consistent, not a pending seam:**

`cruce.util.ts`'s `OrigenAplicacion` interface (`numeroCompleto`/`fechaRecibo`) and `cuentaCarteraDeLinea`'s `LineaParaDesglose` (`cuentaCartera`/`cuentaIngreso`/`tipoConcepto`) both read either side of their duck-typed pair (`Recibo`/`SaldoInicialAnticipo`, `FacturaLinea`/`SaldoInicialLinea`) — all four schemas now use the same Spanish names, so there is no longer a one-sided-rename trap here. If a *future* schema introduces a new duck-typed read via one of these shared interfaces, grep for `cuentaCarteraDeLinea`, `OrigenAplicacion`, and `decrementarSaldoDocumentoOrigen` first — those are the exact seams where a "rename this schema's fields" batch has to touch two schemas at once instead of one.

Mongoose's own `timestamps: true` fields (`createdAt`/`updatedAt`) stay as-is
— framework metadata, not domain vocabulary. Don't hand-roll a Spanish
equivalent (`creadoEn`) alongside them.

## Layout and where new code goes

```
src/
  main.ts              bootstrap: global prefix, ValidationPipe, shutdown hooks
  app.module.ts        composition root — register every new feature module here
  config/              env.validation.ts (Joi), app.config.ts (typed, via ConfigService)
  contracts/index.ts   the Spanish API shapes — see "the contract law"
  common/              cross-cutting, @Global CommonModule
    redis/ firebase/ guards/ decorators/ tenant/ interfaces/ utils/ pdf/ scripts/
  modules/
    casl/              authorization vocabulary, permission map, PoliciesGuard
    <feature>/         one folder per business domain
```

A feature module is `modules/<name>/` with `<name>.module.ts/.controller.ts/.service.ts/.mapper.ts`, `dto/`, colocated `*.spec.ts` — registered in `app.module.ts`. Mongo schemas live under `database/schemas/<feature>/`, not inside the module. Shared infra belongs in `common/`, exported by the `@Global` `CommonModule` (inject the token directly, e.g. `@Inject(REDIS_CLIENT)`).

## Code conventions

- Comments/identifiers/JSDoc: **English**. Test descriptions and end-user strings: **Spanish**.
- Every exported function/class/provider carries a JSDoc explaining *why*, not *what* — but keep it to what's non-obvious; don't restate the signature in prose.
- Prettier (single quotes, trailing commas). ESLint `recommendedTypeChecked` — don't silence a rule inline without explaining the trade-off.
- Imports are **relative**. The `@/*` alias exists in `tsconfig.json` but is **not** wired in `.swcrc` — an `@/` import typechecks then fails at runtime.
- Tests: Jest, colocated `*.spec.ts`. Controllers tested by direct instantiation with hand-rolled mocks, not `Test.createTestingModule`, unless DI wiring itself is under test.
- **DTO filenames are Spanish-verb-prefixed** (`guardar-`, `listar-`, `anular-`, `aplicar-`, `cargar-`, `importar-`, `actualizar-`, `distribucion-`, `filtros-`…), matching the action, not an English CRUD prefix like `create-`/`update-`. Follow the existing verb for the action you're adding rather than inventing a new one.

## Gotchas

- **One connection string per service** — `MONGODB_URI`, `REDIS_URL`, never host/port/password split. Joi validates the scheme (pasting the web console URL instead of the connection string is the easy mistake).
- `common/dns-setup.ts` must stay the **first import** of `main.ts` and of every script that opens Mongo (SRV lookup), and `common/scripts/load-script-env` the **second** (before `../app.module`, when the script boots the app): `ConfigModule.forRoot` validates `process.env` while `app.module.ts` is being evaluated, so `.env.<name>` has to be loaded before that import. A script's `main` starts with `await confirmScriptEnv()`. `seed/scripts-entorno.spec.ts` fails if a script that opens Mongo (`createApplicationContext` or `mongoose.connect`) breaks either rule.
- Script env files: `--env=<name>` loads `.env.<name>` (all `.env.*` are git-ignored except `.env.example`) as the single source: its values replace the shell's, variables it omits are NOT taken from the shell or from the plain `.env`, and `AppModule` builds `ConfigModule` with `ignoreEnvFile` (`config/config-module-options.ts`, switched on by `load-script-env` via `common/scripts/script-mode.ts`; a server boot never imports it, so it is unchanged). Joi still fails loudly for a missing required variable; omitted optional ones are listed in a warning. `seed:admin` therefore needs `ROOT_ADMIN_EMAIL` inside the file, and absent `COMPTABLE_*` variables mean the integration is off. The guard trusts the env NAME, not the database behind it. For the two scripts that take their own `--db=<name>` (`sembrar:consecutivos`, `limpiar:indices-ingles`), that name overrides the URI's database and is the one the guard prints and asks to type.
- `--` and PowerShell (reported, NOT verified here): on Windows PowerShell with npm >= 9 the `--` may be consumed before reaching the script, so `--env` is lost and the script stops with the usage message. Workarounds to try: `npm.cmd run <script> -- --env=<name>`, or quote it: `npm run <script> '--' --env=<name>`.
- `/health/ready` also runs `integracion-comptable` (`modules/health/integracion-comptable.health.ts`): it reads `COMPTABLE_API_URL` / `COMPTABLE_HMAC_SECRET` and fails on a half-set pair, a URL that is not an `http(s)` URL, carries credentials/query/fragment, or does not end in `/api/v1` (the one thing Joi's scheme check misses; without the prefix every Comptable route 404s). Neither set = `up` with `omitido`. Config only, no call to Comptable; it is NOT in `GET /health` (the Dockerfile HEALTHCHECK), because a bad URL is fixed by a redeploy, not a restart.
- `/health/ready` also runs `frontend-url` (`modules/health/frontend-url.health.ts`): with mail configured it fails when `FRONTEND_URL` is missing or is not a bare http(s) origin (a path, query, fragment or credentials would end up in every invoice link); mail not configured = `up` with `omitido`. It names the setting and never echoes the value, and makes no network call. The invoice send enforces the same rule (`diagnosticarFrontendUrl`): `POST /envio-facturas/procesar-pendientes` answers 409 before claiming or auditing anything, after the SendGrid 409. "Pasos por ambiente": set `FRONTEND_URL` (https in production) before deploying the per-address invoice send; readiness detects a miss.
- Redis: one shared client (`common/redis/redis.provider.ts`) with an `error` listener and a capped `retryStrategy`. Don't open ad-hoc clients.
- Redis consumers: `LockService` (cron locks and the block-billing ingest lock) and `LimiteIntentosService` (fixed-window counter for the public access-link redeem; fails closed). One shared client; don't open ad-hoc ones.
- `pdf-lib` (writing PDFs) is core. `pdfjs-dist` (exact version `6.2.108`, ESM) is used ONLY by the transitional block-billing adapter (`modules/facturacion-bloque/`) to detect units in externally produced PDFs; no financial module reads PDFs.
- `npm run build` skips typechecking (`typeCheck: false`, SWC). A green build proves nothing about types — use `npm run typecheck`.
- What the SWC build compiles into `dist/` is decided by `builder.options.ignore` in `nest-cli.json` (`**/*.spec.ts`, `**/testing/**`), NOT by the `exclude` of `tsconfig.build.json`, which the SWC builder never reads. Spec helpers go in a `testing/` folder (`modules/casl/testing/`, `modules/envio-facturas/testing/`) so they stay out of the image.
